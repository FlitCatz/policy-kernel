**버전·라이브러리 종속성과 옵션화 검토 — 2026-09-10**

검토 대상: `5841d8baece42a251d80f73467b77af403e957f1` (`feat/task-14-consuming-acceptance`). 사용자가 특정 버전·라이브러리에 종속된 부분을 옵션화할 수 있는지 검토하도록 요청했다. 이 문서는 코드 조사와 임시 Rust 입력 실험의 결과 및 권고를 기록한다. 옵션화 구현이나 대체 도구의 실행 호환성 인증은 수행하지 않았다.

이전 [최종 코드베이스 검증](2026-09-10-final-codebase-verification.md)의 대상은 `235fe2c`이다. 이번 검토는 후속 수정과 1.0.2 템플릿이 포함된 위 커밋을 기준으로 한다.

**결론**

옵션화할 수 있다. 종속성은 주로 소비 프로젝트용 프로필, bootstrap, 인수검증기에 모여 있다. `policy-core`는 Vite·Vitest·.NET을 직접 사용하지 않으며, 이들의 선택과 정책 판정이 분리되어 있다.

권장 방향은 **도구와 버전을 선택할 수 있게 하되, 실제 검증에 사용한 조합은 정확히 고정하고 증거에 기록하는 것**이다. 선택 가능한 범위를 넓히는 작업과 증거의 정확성을 유지하는 작업을 함께 설계해야 한다.

**종속 지점과 옵션화 범위**

| 대상 | 현재 상태 | 옵션화 방향 |
| --- | --- | --- |
| Node·npm·.NET SDK 버전 | 프로필 외에 설치기·인수검증기에도 중복 고정 | 선택한 버전을 한곳에서 정의하고 생성 설정·버전 검사·CI에 반영 |
| Vite·Vitest·ESLint·Playwright | 설치기가 특정 조합과 패키지 버전을 요구 | 기본 프리셋과 사용자 지정 도구 조합 지원 |
| npm | yarn/pnpm/bun lockfile을 충돌로 처리하며 npm 설치·감사를 사용 | 설치, 잠금파일 검증, 감사를 묶은 패키지 관리자별 어댑터 |
| .NET 대상과 프로젝트 구조 | `net9.0`, `App.csproj`, 정해진 테스트 프로젝트 경로에 결합 | SDK, 대상 프레임워크, 앱·테스트 프로젝트 경로를 각각 선택 |
| 테스트 보고서 | Vitest JSON·Playwright JSON·TRX만 지원 | 보고서 형식별 Rust 어댑터 추가 및 호환성 검증 |
| 프로필 종류·릴리스 | 세 프로젝트 종류와 `1.0.0`·`1.0.1`·`1.0.2`를 Rust 코드에서 열거 | 계약 버전과 프로필 릴리스를 분리하고 사용자 프로필 허용 |
| Rust·내부 crate 버전 | Rust 1.95.0과 workspace dependency 버전을 고정 | 사용자 실행 옵션보다 중앙 버전 관리와 빌드 호환성 검증으로 관리 |
| GitHub·운영체제 | GitHub 전용 관측 계약과 Linux/macOS·Unix 구현에 결합 | 단순 옵션 추가 이상의 별도 플랫폼 어댑터 작업 필요 |

Rust 구현 언어 정책은 유지한다. 내부 crate를 실행 시 교체하는 옵션은 이번 요구를 해결하기 위한 우선 과제가 아니다.

**코드에서 확인한 제한**

- [ProjectSensor](../../../crates/project-verification/src/profile.rs)의 35행부터 명령, 기대 버전, 입력 파일, JSON pin, 환경 allowlist, 제한시간을 데이터로 받는다. 기존 구조를 확장 기반으로 사용할 수 있다.
- 같은 파일의 134행부터 프로필 릴리스를 세 버전으로 제한하고, 232행부터 프로젝트 종류와 필수 컴포넌트를 고정한다. 새 프로필을 배포할 때 현재는 Rust 코드 변경도 필요하다.
- [bootstrap 감지 로직](../../../bootstrap/src/plan.rs)의 157행부터 Vite 부재 또는 Next.js·react-scripts·Angular·Jest 존재를 충돌로 처리하고, 특정 패키지 버전 문자열을 요구한다. 205행부터 `App.csproj`, 225행부터 `net9.0`, 253행 부근에서 npm 외 lockfile을 제한한다.
- [bootstrap 템플릿 로직](../../../bootstrap/src/templates.rs)은 릴리스 자산을 `include_str!`로 내장하고 Node 버전 등을 직접 렌더링한다. 현재 [설치 선택값](../../../bootstrap/src/plan.rs)은 profile/release/components이며 독립적인 도구·버전 선택 필드가 없다.
- [보고서 처리](../../../crates/project-verification/src/reports.rs)는 세 가지 `ReportFormat` enum으로 제한한다. 새 테스트 도구가 다른 보고서 구조를 내보내면 명령 변경만으로 지원할 수 없다.
- [실행 준비](../../../crates/project-verification/src/run.rs)의 121행은 `backend:dependencies`라는 센서 ID에 NuGet XML 검증을 연결한다. 도구 선택을 일반화할 때 이런 도구별 검증도 함께 분리해야 한다.
- [인수검증 실행기](../../../acceptance/src/execution.rs)는 런타임 버전, npm 설치, Playwright 설치, .NET 프로젝트 경로와 실패 시나리오를 직접 정의한다. 프로필 옵션을 추가하면 인수검증과 CI도 같은 선택을 사용해야 한다.

특히 parser 식별자 `vitest-json-3.2.4/v1`은 실제 도구 버전이 반드시 3.2.4여야 한다는 의미가 아니다. 현재 동일 파서가 Vitest 4.1.11에도 사용된다. [보고서 계약 문서](../../integrations/report-formats.md)는 parser 식별자의 역사적 이름과 실제 producer 버전을 구분한다. 옵션화에서도 **파서 계약 버전, 지원 producer 범위, 실제 실행 버전**을 구별해야 한다.

**실제로 확인한 입력 확장 범위**

현재 1.0.2 React 프로필을 읽고 `parse_profile`에 변경 입력을 전달하는 임시 Rust 프로그램을 실행했다.

| 입력 | 관측 |
| --- | --- |
| 기본 프로필 | accepted |
| Node의 기대 출력 문자열을 `v99.0.0`으로 변경 | accepted |
| build 명령을 `custom-builder build`로 변경 | accepted |
| 프로필 자산 버전을 `2.0.0`으로 변경 | rejected |
| 프로젝트 종류를 `custom-project`로 변경 | rejected |
| 보고서 형식을 `jest_json`으로 변경 | rejected |

여섯 관측은 예상과 일치했고 프로그램은 exit 0으로 종료했다. 앞의 두 변경 성공은 입력 구조가 수용된다는 뜻이다. Node 99나 custom-builder를 설치·실행하지 않았으며, 해당 조합의 호환성이나 bootstrap 지원을 증명하지 않는다.

임시 재현 소스는 `/private/tmp/policy-options-probe-5841d8b/src/main.rs`, 실행 산출물은 `/private/tmp/policy-options-probe-target-5841d8b`에 있다. 저장소 구현에 편입하지 않았으며 영구 보존 자료가 아니다.

**권장 구조와 작업 순서**

1. **버전·경로 설정을 통합한다.** SDK, 패키지 버전, 프로젝트 경로의 중복 상수를 제거한다. 선택값에서 프로필, 설치 설정, 버전 검사, CI 입력을 일관되게 도출한다. 최초에는 기존 도구 조합을 유지하면서 검증할 옵션 범위를 제한할 수 있다.
2. **기본 프리셋과 사용자 프로필을 구분한다.** 기본 프리셋은 검증된 시작점을 제공하고, 사용자 프로필은 프로젝트의 기존 도구와 경로를 표현한다. 새 자산 버전이라는 이유만으로 계약 파서를 수정하지 않도록 계약 호환성과 자산 릴리스를 분리한다. 설치기의 자산 출처·내용 검증은 유지한다.
3. **필요한 대체 도구부터 어댑터를 추가한다.** 패키지 관리자, 빌드·정적 검사, 테스트 보고서 형식을 각각 다룬다. 지원한다고 선언할 각 조합에 실제 정상·실패·빈 보고서·수정 후 재검증 사례를 마련한다. 조합 전체를 검증하기 전에는 지원 범위를 확대했다고 주장하지 않는다.

설치기는 선택값을 계획과 영수증에 포함해야 한다. 기존 릴리스의 파일 렌더링·소유권 확인·복구·제거 결과가 달라지지 않도록 과거 의미를 보존해야 한다. 옵션 추가에 계약 변경이 필요하면 버전을 명시적으로 구분한다.

확정된 실제 버전, argv, 설정, 잠금파일, 파서 식별자는 기존 digest와 정책 연결에 포함한다. 버전 선택 범위를 허용하더라도 실제 실행한 버전을 흐리게 기록해서는 안 된다. 도구 변경 후에도 필수 테스트, 빈 보고서 거부, 모든 대상 의존성 그래프의 감사, 이전 head 증거 거부는 유지한다.

단순히 버전 문자열을 느슨하게 비교하거나 임의 명령을 성공 코드만으로 수용하는 방식으로는 이 요구를 충족하지 못한다. 선택 가능한 설정과 실행·결과 검증을 함께 확장해야 한다.

**외부 도구 계약 확인**

- [npm ci 공식 문서](https://docs.npmjs.com/cli/v10/commands/npm-ci/): 기존 lockfile을 요구하고 manifest와 다르면 오류를 내며 lockfile을 갱신하지 않는다.
- [pnpm frozen-lockfile 공식 문서](https://pnpm.io/cli/install#--frozen-lockfile): lockfile 생성·갱신 없이 설치하고 누락 또는 불일치를 실패로 처리한다. npm에서 pnpm으로 바꿀 때도 이런 의미를 보존해야 한다.
- [.NET global.json 공식 문서](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json): SDK `version`은 완전한 버전 문자열이며 허용 범위 선택은 별도 `rollForward` 정책으로 표현한다. SDK 선택 정책과 실제 실행 버전 기록을 구분해야 한다.

본 검토에서는 위 문서와 현재 소스를 대조했다. 새로운 대체 프레임워크·패키지 관리자·운영체제의 전체 실행 검증이나 옵션화 구현은 수행하지 않았다.
